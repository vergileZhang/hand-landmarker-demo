# 手势识别与 MCP 触发阶段汇报 PPT 设计

## 目标与受众

为非技术管理者制作一份 16:9 中文阶段汇报，控制在约 5 分钟、8 页。汇报不解释算法公式，重点回答三个问题：目前做到了什么、当前还有哪些明确边界、下一周如何验证交互与工程落地。

## 叙事结构

1. 封面：手势识别与 MCP 触发能力阶段汇报。
2. 阶段结论：本地摄像头实时识别链路已经跑通，下一阶段转向稳定触发和工具化。
3. 当前效果：8 类有效静态手势、每只手 21 个关键点、最多 2 只手、左右手和置信度；加入本机实测推理延迟。
4. 已实现与未实现：明确列出极端平面旋转、手心/手背切换、超过 2 只手、上下左右方向、动态手势、双手组合语义、遮挡与弱光等限制，并区分“配置限制”“鲁棒性问题”“能力尚未开发”。
5. 四种交互方式：单次识别、常驻实时、文字/语音指令唤醒会话、Thumb Up 低频唤醒；比较响应、资源、隐私、误触发和实现难度。
6. 推荐方案：用状态机组合指令会话与 Thumb Up 低频唤醒；说明 MCP 负责工具接口，MediaPipe 负责持续识别，本地事件层负责主动动作触发。
7. 工程落地难点：防抖、冷却、摄像头权限、资源占用、错误恢复、MCP 客户端兼容和危险动作二次确认。
8. 一周实验计划：按天安排交互选型、稳定触发、事件桥、MCP 工具、端到端动作与验收测试。

## 视觉方向

延续现有 Demo 的深蓝、青绿色本地计算视觉风格。使用真实 Demo 截图作为主要证据；数字页突出 8 类手势、21 点和实测延迟。避免大段技术文字，限制页采用“已实现 / 当前边界”强对比，交互页采用四方案对比，架构页只保留一条清晰数据流。

## 数据原则

- 8 类手势、21 个关键点和最多 2 只手来自当前代码配置。
- 延迟必须在当前机器与浏览器上实测，并标注为“本机浏览器实测”，不得当作所有设备的承诺。
- 尚未执行的鲁棒性和工程指标只作为下一周实验项目，不填写虚构结果。
- “低功耗 Thumb Up”在幻灯片中称为“低频/低负载唤醒”，说明摄像头仍处于开启状态。
