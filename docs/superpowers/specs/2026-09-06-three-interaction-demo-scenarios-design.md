# 三类手势交互 Demo 场景设计

## 1. 目标

围绕被动响应型、用户唤醒型、持续监听型分别实现一套可独立展示的用户场景，使非技术观众能够直观看懂：谁发起交互、摄像头何时工作、手势如何转化为电脑动作。

本阶段复用现有 8 类静态手势，不增加挥手、左右滑动等动态手势：张开、握拳、OK、向上指、拇指向上、拇指向下、胜利/V、我爱你。

## 2. 统一交互语义

三套 Demo 采用混合映射：确认、取消、暂停和退出等通用语义保持一致，业务动作由当前场景解释。

| 手势 | 通用语义 |
|---|---|
| 拇指向上 | 确认、开启或向前 |
| 拇指向下 | 取消、拒绝或向后 |
| 张开手掌 | 暂停、暂不处理或隐藏 |
| 握拳 | 结束、退出或锁定 |
| OK | 确认当前结果无误 |

## 3. 场景一：持续监听型——文档与 PPT 翻页

### 3.1 用户场景

用户正在阅读 PDF、Word 或展示 PPT，摄像头持续识别手势，用户无需触碰键盘即可控制页面。

### 3.2 手势映射

| 手势 | 动作 |
|---|---|
| 拇指向上 | 下一页，等价于 Right Arrow / Page Down |
| 拇指向下 | 上一页，等价于 Left Arrow / Page Up |
| 张开手掌 | 暂停或恢复手势控制 |
| 握拳 | 结束持续监听模式 |

### 3.3 演示流程

1. 用户打开 PDF 或 PPT，并点击“持续监听”。
2. 页面显示摄像头画面、当前手势和“监听中”状态。
3. 用户做拇指向上，文档进入下一页。
4. 用户做拇指向下，文档返回上一页。
5. 用户张开手掌，界面进入“已暂停”；再次张开后恢复。
6. 用户握拳，摄像头关闭并退出翻页模式。

### 3.4 防误触规则

- 手势需连续稳定 5 帧且置信度不低于配置阈值。
- 动作按手势状态上升沿触发，不因持续保持同一姿势而连续执行。
- 执行一次翻页后进入 800 ms 冷却。
- 同一手势再次执行前，必须先检测到无手或其他手势。

### 3.5 MCP 与本地职责

- MCP 工具负责 `start_page_control`、`pause_page_control`、`stop_page_control` 等会话控制。
- 本地识别服务持续处理视频帧并产生稳定手势事件。
- 本地动作执行器将事件转换为系统按键，不让大模型逐帧调用工具。

## 4. 场景二：被动响应型——AI 请求用户确认

### 4.1 用户场景

AI 准备执行需要确认的操作时，由电脑主动发起手势请求。推荐演示问题为：“AI 已生成会议摘要，是否保存到本地？”

### 4.2 手势映射

| 手势 | 动作 |
|---|---|
| 拇指向上 | 确认并保存 |
| 拇指向下 | 取消操作 |
| 张开手掌 | 暂不处理，关闭本次请求 |
| OK | 确认当前内容无误并保存 |

### 4.3 演示流程

1. AI 显示会议摘要和确认卡片。
2. 系统调用手势确认工具，摄像头临时启动并显示 8 秒倒计时。
3. 用户做拇指向上或 OK，页面显示“已确认并保存”。
4. 用户做拇指向下，页面显示“操作已取消”。
5. 用户张开手掌或超时未响应，页面显示“暂不处理”。
6. 完成本次选择后立即关闭摄像头，不继续监听。

### 4.4 MCP 工具接口

```text
request_gesture_confirmation(
  question="是否保存会议摘要？",
  positive_action="保存",
  negative_action="取消",
  timeout_seconds=8
)
```

返回结果限定为 `confirmed`、`cancelled`、`deferred`、`timeout`，由调用方决定后续业务操作。

### 4.5 安全规则

- 每次工具调用只接受一个有效结果，识别完成后立即结束。
- 删除文件、发送消息、支付等高风险动作不能仅凭一次手势直接执行。
- 确认卡片必须同时显示问题、即将执行的动作和剩余时间。

## 5. 场景三：用户唤醒型——直播无声控制

### 5.1 用户场景

直播环境嘈杂，或者主播不方便使用语音和键盘时，通过拇指向上主动唤醒一段手势控制会话。

### 5.2 状态与手势映射

| 状态 | 手势 | 动作 |
|---|---|---|
| 守候 | 拇指向上保持约 1 秒 | 唤醒手势控制会话 |
| 控制 | 胜利/V | 切换下一个直播画面或素材 |
| 控制 | OK | 展示并固定当前商品卡片 |
| 控制 | 向上指 | 显示关注或互动提示 |
| 控制 | 张开手掌 | 隐藏当前浮层 |
| 控制 | 握拳 | 退出控制会话并返回守候状态 |

### 5.3 演示流程

1. 页面进入守候状态，仅低频检测拇指向上。
2. 主播保持拇指向上约 1 秒，界面提示“手势控制已开启”。
3. 主播做胜利/V，系统切换直播素材。
4. 主播做 OK，系统展示并固定商品卡片。
5. 主播向上指，系统展示关注提示。
6. 主播张开手掌，当前浮层被隐藏。
7. 主播握拳，系统退出控制状态并恢复低频守候。

### 5.4 状态与资源规则

- 守候状态建议以 3–5 FPS 检测拇指向上；是否属于低功耗需通过 CPU、能耗和温升实测确认。
- 唤醒后切换至正常实时识别帧率，并启用完整手势集合。
- 控制状态 15 秒无有效操作后自动返回守候状态。
- 界面必须持续显示“守候中”或“控制中”，避免用户不知道摄像头当前用途。

### 5.5 MCP 与本地职责

- Thumb Up 守候检测属于本地常驻服务，不能依赖大模型逐帧轮询。
- 唤醒后，本地服务产生 `gesture_session_started` 事件。
- MCP 工具负责查询状态、修改手势映射、停止会话或将稳定事件交给外部应用。

## 6. 共用组件

三套 Demo 共用以下组件，场景之间仅替换状态机和动作映射：

1. 摄像头与 MediaPipe Gesture Recognizer。
2. 5 帧手势平滑与置信度门槛。
3. 上升沿触发、动作冷却和超时控制。
4. 场景状态机与手势动作映射表。
5. 浏览器事件层与可替换的动作执行器。
6. MCP 会话控制与结果查询接口。

## 7. 演示顺序

推荐按照复杂度逐步增加：

1. 被动响应型：一次请求、一次手势、一次结果。
2. 用户唤醒型：低频守候、主动唤醒、短时连续控制。
3. 持续监听型：长时间识别并连续控制外部应用。

对应讲解口径为：“电脑问、人回答；人先发起、再控制；系统一直等待手势。”

## 8. 验收标准

- 三套 Demo 均能单独启动、停止和恢复初始状态。
- 每套 Demo 的发起方、摄像头状态和手势动作在界面上清晰可见。
- 同一静态手势持续保持时不会重复执行动作。
- 被动响应型在识别、取消或超时后释放摄像头。
- 用户唤醒型能从守候进入控制，并在握拳或超时后返回守候。
- 持续监听型能完成下一页、上一页、暂停/恢复和退出。
- 所有真实动作均经过白名单，失败时显示明确反馈且不重复执行。
